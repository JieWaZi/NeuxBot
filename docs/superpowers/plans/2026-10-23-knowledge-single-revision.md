# Wiki 单次整理内容版本实施计划

> 按用户明确授权直接修复；使用 writing-plans 梳理后以 executing-plans 内联实现，遵循 test-driven-development。不提交或发布，保留其他修改。

**目标：** 同一个整理任务对每个 Wiki 页面最多产生一个内容版本；中间写入、恢复与重试不增加历史；成功贡献不重新生成；保留当前加历史合计最多 50 版。

**架构：** 复用现有 Receipt 为任务与页面保存已分配内容版本，与页面写入同事务。后续写入合并当前版本，保留第一次替换前的快照；新页保持 v1。自动维护只更新派生信息，仍校验页面版本与读取时间。人工或其他任务写入后，原任务不得继续覆盖。无数据库结构变化；整页 HTTP 请求回传已有的页面更新时间，智能体整页命令增加读取时间参数。

**技术栈：** Go、GORM、真实临时 SQLite。

**需求依据：** 本会话用户确认的单次整理、成功结果复用、统一 50 版规则。

## 任务与接口

- [x] 存储回归先失败：同任务连续十次更新只增加一版，新页仍 v1；无变化不增版；新任务独立增版；同任务重试尝试不重复增版；并发人工编辑和事务回滚保持安全。
- [x] `internal/store/page.go`、`lite.go`：写入层接入任务版本回执，保留授权、来源验证和原始快照；`wiki_page.go` 的自动维护使用时间与版本校验，不创建历史。
- [x] 管线回归先失败：多批来源更新共享页面，最终历史只有一次变更；恢复不重复生成成功页面。调整 `pipeline/lite.go` 摘要链接清理为维护语义。
- [x] 核心全测与 vet、宿主后端全测与 vet、宿主 `pnpm check`；同步 SDK 和架构说明，独立审阅后按哈希应用到原核心仓库。

## 重点验证

- 任务身份不随自动重试或显式尝试改变；任务内版本回执不得跨页、跨库串用。
- 原页面快照不可被中间过程覆盖；相同内容和派生信息写入不产生伪历史。
- 整理期间人工、其他任务更新后，旧任务只能失败，不能以旧版本覆盖新正文。
- 保留跨进程恢复、贡献回执原子性、来源撤回和取消屏障；新任务正常创建下一版本。
- 上限仍为 50（当前 + 最多 49 个快照），不区分编辑来源。

## 边界

不重跑真实付费模型、不改写现有用户 Wiki、不清理用户旧历史、不重启应用。先在当前核心副本实现；应用时逐文件核对基线，避免覆盖并行工作。

- 宿主本地、远端和智能体整页入口原样转发读取时间；编辑器固定打开时的快照，后台刷新不能更新旧草稿的并发屏障。核心使用毫秒严格递增的写入时间，避免前端时间精度损失；事务失败不修改调用者的读取屏障。相关核心、API、智能体和组件回归均已通过。
