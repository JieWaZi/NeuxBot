# Wiki 部分失败恢复与修订保留实施计划

> 执行方式：按 executing-plans 在当前会话逐项实现；使用独立核心临时副本验证，保留宿主所有无关改动，不提交或发布。

**目标：** 一个页面失败时，已完成的文档提取和已落库页面贡献不再次调用模型；确定性拒写保留明确诊断；修订历史按统一最多 50 个版本（含当前页）裁剪。

**架构：** 复用知识核心现有 Stage 保存文档提取结果，复用 Receipt 在页面事务中原子记录已应用贡献，不新增数据库表或公开 API。恢复仍校验原任务尝试、不可变来源和发布权限。SQLite 同实例的短事务串行，模型调用继续并发。

**技术栈：** Go、GORM、SQLite；核心独立模块通过本地 go.work 联合验证。

## 排查证据

- 三份来源中一份重跑六次；首个来源任务最终为部分失败。
- 重新生成的摘要表格行标识损失超过现有 20% 阈值，导致拒写后整份重试。
- 同期存在 SQLite busy；固定 WeKnora 也会重新入队存在未应用页面的来源，不能宣称上游没有此问题。

## 任务

- [x] 持久化完整文档 Map 结果；页面写入与贡献回执同事务；恢复只处理缺失贡献。
- [x] 原样保留表格保护，对确定性拒写输出具体页面、丢失行数量与总数，不循环消耗模型预算。

- [x] 接通统一 50 版修订裁剪策略，验证自动与人工历史、事务回滚、版本继续递增。

## 验证边界

不使用真实付费模型重跑，不修改用户当前 Wiki 或任务状态；本地联合开发不等于已发布模块或已更新运行中应用。

用户调整：统一最多 50 个版本，不区分来源；按当前版本加最多 49 个历史快照落实。

- 核心与宿主后端 `go test ./...`、`go vet ./...` 通过；回归覆盖进程恢复、共享页面、人工摘要保护、贡献回执事务回滚、确定性拒写和统一版本上限。
- 独立审阅发现的恢复后摘要别名链接缺失问题已修复并补回归，复审未发现新阻断问题。
- 宿主 `pnpm check` 在文档检查阶段被既有、与本任务无关的进度文件所含个人目录拦住，未改该文件或扩大检查例外。

- 没有重跑真实模型、改写现有用户资料、清理当前历史或重启运行中应用；已有超限历史在页面下一次成功写入事务中裁剪。
