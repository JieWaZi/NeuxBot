# 14 让同一 PR 的更新和等待回到原工作

## 用户问题

伙伴发现 PR #42 后又收到评审意见，用户还交代“等 CI 通过再继续”。若把每条事件都新建成一项工作，同一 PR 会出现互不相干的结论。若按 PR 号吞掉所有重复输入，后来的 CI 成功也无法唤醒原请求。

## 解决方案

将一次来源事件、来源中的讨论对象和主体接受的工单分别寻址。对已跟进 PR 的新事件，给订阅它的工单追加输入。对已登记的等待条件，只有匹配事件能唤醒原请求。用户可引用公开发现，继续交代同一项工作。

## 用户故事

1. **14.1** 我让伙伴持续跟进 PR #42。新建和后续评审各被处理一次，可从公开报告看到原 PR、原工单和实际责任主体。
2. **14.2** 同一 PR 可给几项工作提供不同上下文。某张单只参考这条动态时，其他有权负责的规则仍可判断是否接单。
3. **14.3** 我登记“等 CI 通过再继续”后，合格事件会唤醒原工作。原线程无法接收额外唤醒时，我能从本次例行运行查到发生了什么。

## 实现决定

依赖第 05 项的 Ticket、授权及工作输入，第 07 项的可查询投递收据和第 13 项的来源事件身份。为来源讨论保存订阅，每张单按“工单＋事件”各接纳一次，分清已记入、已投到尝试、已在回合读入。先分发订阅，再按主讨论判断是否已有工单负责；仅收作上下文仍可进入评估。同一主讨论最多一个在途评估，冻结事件批次、工单和策略版本。评估时又到的新输入留给下一批，过期评估重新判断。验权以已生效规则及实际动作范围为准。[目标领域与授权](../superagent-conversation-architecture-cn.md#一件工作从哪里来) · [DeepSeek 订阅扇出](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/core/intake.ts#L30-L59) · [输入投递与读取](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/8c32a9dc5d72c033816c6a8110b37f40cf94fba4/src/core/assignments.ts#L33-L64)

等待记录持有原请求的投递身份和条件，事件按“等待＋事件”结算。另行向原线程投递唤醒时，保存该次投递身份。已归档的普通线程在有资格且有容量时可重开。已删除、无资格、容量不足或投递失败时，事件和处理结果留在触发它的例行运行。工单已经结束时，只有允许重开、所属讨论的人补充请求且原授权重验通过，才进入同一工单的新尝试。人工停止的工单需要重新委托。[OpenBot 等待记录](https://github.com/nightly-labs/openbot/blob/100c60e893eda3ce4761b4d10001a8e490c43536/src/backend/agent-waits/agent-wait-store.ts#L60-L83) · [事件唤醒](https://github.com/nightly-labs/openbot/blob/100c60e893eda3ce4761b4d10001a8e490c43536/src/backend/agent/routine-scheduler.ts#L1175-L1219) · [已归档线程重开](https://github.com/nightly-labs/openbot/blob/100c60e893eda3ce4761b4d10001a8e490c43536/src/backend/agent-tasks/agent-tasks.ts#L249-L267)

## 测试与人工验收

- **先自动化。** E1 建立 PR #42 跟进单，重放 E1，再发评审 E2 和同号但不同仓库的变化。预期同单只追加 E2 一次。第二张上下文订阅单独得到自己的 Input。投递后中断、尚未读入的输入应按原身份恢复。策略变更期间完成的旧评估不能照旧接单。
- **验证唤醒。** 给原请求登记 CI 成功等待，依次发送 CI 失败、CI 成功及其重放，原请求只续办一次。分别覆盖归档可重开、已删除、容量满及额外投递失败，后三者在例行运行可查。人工停止后再次收到动态，断言旧尝试不能重启。
- **再由用户桌面验收。** 在已授权的测试 PR 下，从一次提醒回复“等 CI 通过再总结”，观察随后的 CI 结果。从原工作核对等待、输入和续办回合，查看最终报告的归属。记录事件、工单、等待、运行与会话标识。

## 不在本项范围

PR 的外部评论和代码修改需另有授权。工作流步骤的人工决定见第 15 项。业务等待、CLI 提问和审批分别保留自己的处理入口。

## 验证记录

- 原生 Codex 协议夹具覆盖 E1 的实际工作来源与原自动运行公开引用，E1 重放不再派工。E2 两次提交沿用原输入身份，只在同一工作记录显示一条带来源链接的回件。
- SQLite 工单测试覆盖不同仓库的同号 PR、一个事件的负责与上下文订阅、CI 匹配和重放、已接纳与已读的分界，以及经证明未派发时保留原事件的恢复。
- 调度测试覆盖同一讨论的语义评估互斥、旧策略的待派事件被标记为规则已变更，以及永久无法续办时在实际回退运行中保留原因。工单测试另行核对人工停止后不会由新 CI 结果启动原尝试。
- 前端定向测试覆盖来源目录声明持续跟进选项，以及切换到不支持跟进的目标后隐藏该选项。
- 真实 GitHub 仓库变化与桌面人工验收待执行。产品的普通 Chat 当前没有归档重开入口。独立伙伴已开放持续跟进，团队事件规则可以继续使用常规事件运行。

## 接手说明

先用同一 PR 的两个不同时刻证明来源身份和工单身份可分别重放，再接等待及归档分支。交付本项时写明自动化、真实事件与桌面验收状态。完成本项后停止，后续规格另行启动。
