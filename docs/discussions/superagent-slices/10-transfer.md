# 10 整单移交后由新负责人接手，旧结果不能结案

## 用户问题

委派一部分工作与把整件事交给另一位负责人有不同后果。混用两者会让旧执行越权结案，或丢失最初交办的位置。

## 解决方案

用户明确要求整单移交时，保留同一张 Ticket、历史与回址。新负责人接手后，旧负责人迟到的报告只供追溯。

## 用户故事

1. 作为交办人，我希望将整件事从 A 交给 B 后仍能沿原消息追踪。
2. 作为接手人，我希望看到当前责任、授权和必要的历史，以便继续工作。
3. 作为原负责人，我希望明确知道交接完成，以免重复回报或修改结论。

## 实现决定

- 移交在同一次提交中变更工单责任主体和责任版本、封存原尝试，保留 Ticket 及原始回址。复用委派已有的资格校验和报告契约。
- 普通点名、询问意见和委派子任务沿用原语义。明确移交需要目标有资格接单，交接完成后旧版本不能推进新状态。
- 移交沿用聊天输入框。引用原交办或回报并发送 `/移交 伙伴或团队全名`，可从下一行补充交接说明。原会话保留交接通知，后续引用交给同一工单的接手人。
- 未结的子单、待答问题与未消费回件继续属于原工单。提交前校验接手人的本地运行配置，派发前重新核对任职资格。已接纳但无法派发的移交可以重新转交。

## 测试与人工验收

1. 通过同一公开交办将 A 的单转给 B，在确认交接后注入 A 的迟到完成，再让 B 完成。核对工单身份、责任历史、最终收件人和结果次数。
2. 覆盖重复提交、无资格的目标、移交途中退出恢复。检查未成功移交时原负责人仍能继续。
3. 桌面先委派一项子任务，再对另一件事明确移交；从两份工作记录观察责任归属与原会话回报。

## 不在本项范围

自动调整团队成员、跨主体扩大权限、批量转交团队全部工作。

## 验收记录

- 本机认证的显式工单移交入口要求原会话、目标主体、当前责任代次、请求标识与交接内容。相同请求重投返回同一回执。普通点名仍沿现有聊天行为。
- SQLite 回归覆盖原工单身份、旧负责人迟到完成被拒、无资格目标、事务回滚及重启恢复待派发接手。
- 模拟 Codex 通过正式 Core API 让 B 在独立记录接手。普通聊天和主会话各收到一份 B 的回件，引用原交办或 B 的回件均可继续同一工单。原主会话从回件头像打开本次执行的只读工作记录。
- 接手人正在执行时，主会话的引用补充进入同一持久队列。原普通聊天的跨伙伴续办会独立保存用户输入，临时写入失败时由恢复流程补齐。该入口接收文字续办。
