# 09 伙伴和团队逐级委派，报告返回直接请求者

## 用户问题

现有团队派工局限于一个团队线程。用户交代 A 的工作无法经团队 B 再委派给伙伴 C 并回到原请求。

## 解决方案

伙伴和团队按同一主体协议派发子任务。下级报告先回给直接上级；最初交办的会话收到最终报告，同时保留各自的工作记录。

## 用户故事

1. 作为交办人，我希望只跟 A 沟通，就能由 B 和 C 合作交付。
2. 作为团队负责人，我希望在多个子工作都满足成功条件后再推进依赖。
3. 作为接单伙伴，我希望收到足够的指令与授权，并将问题或受阻原因交给能处理的人。

## 实现决定

- 委派创建子 Ticket、依赖和直接回址，父单保持原负责人。伙伴和团队是同一接单协议的主体类型。复用团队已有成员、依赖和报告结算语义。
- 拒绝祖先依赖环。并行普通子任务待成功依赖全部满足；问答型子任务按既有规则归并。业务待决、CLI 提问和审批保留各自的归属。

## 测试与人工验收

1. 从 A 的普通会话交办，A 派给团队 B，B 再交给 C。重投 C 的同一报告、加入旧尝试回调，核对各级只结算一次，原线程只收到一份最终报告。
2. 两项并行子单一成一败，验证成功依赖未提前解锁。分别测试 C 提问、合法答复、拒绝循环委派与撤销授权。
3. 桌面从 A 发起一次多人协作，再从结果打开来源检查负责人、子工作与逐级回件。

## 不在本项范围

整张工单换负责人、重新设计团队界面、将手动新建普通会话转换为群聊。

## 验收记录

- 普通会话交办由模拟 Codex 和实际 `botcli` 通路执行。A 派给团队 B，B 再交给 C。C 和 B 的结果各回直接请求者，A 的原会话收到一份最终报告。
- 原生提问测试验证 C 的问题仍由原来源及执行接收。工作看板定位到 C，合法答案返回该 CLI。错误主体、错误来源、旧执行、无效选项和重复答案均被拒绝。答复后工作沿 C、B、A 返回原会话。
- 业务提问测试验证 B 的原回合结束后，C 的待答回件只唤醒 B 一次。B 通过 `botcli` 读取并答复对应报告，C 收到答案后继续，最终结果仍逐级交还。大量进展回件也不会遮蔽已提交的最终结论。
- 工单回归覆盖结案依赖、迟到回件、循环、撤销团队授权及问答型子工作的失败处理。真实模型和桌面视觉待验收。
