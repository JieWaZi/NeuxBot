# 08 CLI 忙时接纳新交办，重启后按原身份续办

## 用户问题

同一来源运行时不能接纳下一个回合。遇到进程中断或原生 session 丢失，用户难以确定之前交代的事会不会丢失或执行两次。

## 解决方案

工作中也能从主会话或来源提交下一次交办，得到接纳回执；执行资源释放后继续。确认原生会话丢失时仍在同一工单和授权内接力。

## 用户故事

1. 作为正在等待长任务的用户，我希望新交办立刻获得接纳。
2. 作为重启应用的用户，我希望已入队的输入按原归属继续，只执行一次。
3. 作为使用多种 CLI 的用户，我希望临时断连、原生会话确实丢失两种情形得到合适处理。
4. 作为用户，我希望补充当前工作与提交下一件事能沿用现有 CLI 实际支持的交互。

## 实现决定

- 沿用现有 CLI 的排队、steering 与停止语义。按来源及运行资源领取，接纳后记录已有身份，不在前端另维护权威队列。
- 能恢复的原生绑定优先恢复；确认丢失后使用有界交接保留近期输入、已确认报告、引用与授权。领取超时只触发对账，迟到确认不再启动第二个进程。

## 测试与人工验收

1. 从正常发送入口让单回合 CLI 卡在一个可释放的测试闸门，期间从两个视图发后续输入，再释放。验证接纳顺序、回执和运行次数。
2. 重启时令派发器和恢复扫描争用一次领取。覆盖启动回执迟到、临时无法恢复、已确认原生 session 消失；核对工单、原消息与项目范围一致。
3. 桌面在正在工作的伙伴处交代下一件事，等待第一件结束并查看后续执行；通过隔离环境复查重启恢复。

## 不在本项范围

Watchdog 策略、额外账号或额度预检、对不支持的 CLI 强制提供原生 steering。

## 验收记录

- 模拟 Codex 挂起第一轮时，从主会话和对应工作记录各提交一轮。两个入口均取得持久回执。放行后按接纳顺序执行，每条输入沿用原消息和同一工作会话，各接手一次。
- 服务测试用同一数据库重新创建派发器，验证原回执对账、并发唤醒、提交标识重投和附件恢复。原生发送门把执行接纳和实际输入写入同一批次。经过发送门但原生结果未核实时，以原输入对账并保留绑定。
- 模拟派发前及接纳后连续四次读取回执遇到临时数据库错误。恢复后无需再次发送或唤醒，两个输入按原顺序各执行一次。
- 模拟 CLI 原生会话确实缺失时验证只新建一次原生会话，并带上有界交接。恢复结果未核实和传输中断时沿用原绑定。前端回归覆盖回执先于历史刷新、重新打开及接手后消息去重。
- 真实桌面重启待验收。
