# 11 在途工作卡住时停止执行

## 用户问题

一个伙伴反复调用同一工具，另一个伙伴正在等用户批准。前者持续占用执行槽，后者可能几小时都没有新输出。按“多久没说话”统一取消，会中断仍然有效的审批。

## 解决方案

由宿主巡查正在执行的工作。达到巡检条件时，把观测到的原因交给执行宿主，请求停止指定尝试。用户在工作记录看到实际停止结果，已接纳的其他工作按原队列继续，等待审批的卡片仍能处理。

## 用户故事

1. **11.1** 作为交办人，我能看到工作何时因耗时、停滞、重复调用或预算限制而被要求停止，以及宿主是否已确认停止。
2. **11.2** 作为审批人，我可以稍后回答原来的请求，期间巡检不会因等待我而取消执行。
3. **11.3** 作为正在等待回复的用户，我在单回合 CLI 被占用时仍可提交下一条消息，执行槽释放后继续处理。

## 实现决定

复用 Execution 按 Chat 与 Execution 身份取消的入口，以及已有审批、提问、终态和工作记录。第 05 项提供工单与尝试归属，第 08 项提供忙时接纳、排队和执行领取。巡检读取这些权威事实，记录触发条件、最后一次有效进展和所针对的尝试。巡查对象限正在执行且有资格停止的尝试。[执行取消入口](../../../server/services/execution/service.go) · [执行审批](../../../server/services/execution/approval.go)

新增巡检判断时，分别处理总耗时、没有有效进展、重复工具调用和预算耗尽。测试应可控制时钟和阈值。发出取消前复核当前尝试、终态和待审批状态，按同一尝试复查已有取消请求。宿主确认终态后才释放该次执行的占用。工单所有者依据取消原因决定等待、重试或结案。巡检期间不发起账号、额度或模型目录探测。[Go 目标设计](../superagent-conversation-architecture-cn.md#7-持久化恢复与-cli-边界) · [OSA 在途巡检固定源码](https://github.com/kadaliao/open-super-agent/blob/e9722c7462cbf220ece4e03f74257cfc7d19962a/server/crates/osa/src/watchdog.rs#L45-L85)

## 测试与人工验收

- **先自动化。** 用可控时钟让执行 A 停滞、B 等审批、C 持续产出有效进展。跨过停滞阈值后仅 A 收到一次取消。按各自阈值分别验证总耗时、重复调用和预算触发。在扫描后、发出取消前完成 A 或更换尝试，旧巡检不能停止新工作。
- **验证释放。** 用单回合测试驱动占住执行槽，接纳下一条消息。取消回执未明时仍保留原尝试并核实，终态确认后只启动下一条一次。回答 B 的原审批后，B 能继续。
- **再由用户桌面验收。** 在可控测试工具上运行停滞任务，另开一项需批准的工作，提交后续消息。核对工作记录中的停止原因、审批卡仍可用、排队消息最终得到答复。记录执行及审批标识、用到的阈值和实际结果。

## 不在本项范围

插件新事件发现由第 13 项处理。工单的业务停止、移交及重新接单由工单所有者处理。本项不增加巡检设置页。

## 验证记录

- 已通过可控时钟测试。覆盖原尝试停滞、有效进展、审批挂起、四种触发条件、前轮结束、人工停止和工单代次失效。
- 已通过 OpenCode 协议子进程测试。原生取消只发送一次，确认前占位和待决状态仍可读，另一个回合的原审批仍可批准并完成。确认后等候同一占位的输入只进入原生回合一次。主会话和来源的耐久队列另有原入口回归。
- 已通过 Core 重启恢复专项测试。已持久化的停止请求只生成一条终态，原生确认缺失时保留原原因及未确认状态。前端组件测试验证同一工作记录分别呈现等待确认和已确认。
- 桌面人工验收待执行。涉及真实 CLI、审批、主会话队列和工作记录的联动。

## 接手说明

先从执行取消和待审批的现有用例定位可观察状态，再补当前尝试失效与取消回执竞态的测试。交付时分别列出自动化结果与用户桌面验收结果，缺哪项就标哪项待验收。完成本项后停止，后续规格另行启动。
