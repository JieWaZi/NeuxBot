# 13 在聊天和自动任务页订阅仓库动态

## 用户问题

用户希望“这个仓库有新的待评审 PR 就提醒我”。当前自动任务支持定时和本机 API。即使伙伴安装了能查询 PR 的插件，系统也需要知道它是否提供事件、从何时开始观察、哪些变化已经处理。

## 解决方案

让用户在聊天或自动任务页选择已登记的事件来源、限定仓库与动态类型、配置条件及汇报方式。首个来源提供 GitHub 仓库 PR 动态，覆盖从建规则、首次基线、发现新动态到收到带来源或运行链接的独立消息。

## 用户故事

1. **13.1** 我可以一句话要求“每周一发周报，出现新 PR 时提醒我”，看到两个可单独打开和暂停的规则。聊天与管理页指向同一份配置。
2. **13.2** 我能选择当前来源实际支持的字段，查看最近检查、过滤结果、运行和已送达报告。首轮检查仓库已有 PR 不会给我发一批旧提醒。
3. **13.3** 我可以选“现在看一次”检查实际变化，也可以明确选择会派工的“测试”，用测试结果核对配置。

## 实现决定

复用第 12 项的主体授权、规则管理和运行历史，以及持久投递。在本项将每条公开发现链接到可访问的对象或运行，将规则回执链接到规则详情。新增事件触发类型与来源目录。来源声明字段、能力及其支持的轮询、推送或内部匹配方式，管理页按字段绘制表单，Go 校验同一份声明。只提供查询工具的插件可由定时任务调用。首个 GitHub 适配器只申请读取所选仓库动态与按约定向主体汇报的权限。[已有触发类型](../../../server/constants/automatic_task_trigger.go) · [自动任务详情](../../../packages/frontend/src/modules/automatic-task/pages/automatic-task-detail-page.tsx) · [OSA 仓库来源字段](https://github.com/kadaliao/open-super-agent/blob/e9722c7462cbf220ece4e03f74257cfc7d19962a/osa/sources/github_repo.py#L224-L239)

首次轮询记录基线。之后按来源实例和可用事件身份接纳，观察结果及待处理意图先落盘，再按旧游标条件推进。两个 poller 同时返回时游标保持最新已提交进度。推送型来源先验来源，再持久接纳和确认。无稳定事件号或只有有限查询窗口的来源，如实记录可判重或追溯的范围。先匹配确定性条件，配置了语义条件才调用模型。同规则忙时收集后续匹配，完成后继续。运行详情分别记录空检查、检查失败、观察到但被过滤、工作完成后无需报告以及实际送达。[OSA 轮询结果](https://github.com/kadaliao/open-super-agent/blob/c217b8e0dcaaa40bb865febad2deeba483d0e1cd/osa/events.py#L449-L470) · [事件源与测试语义](https://github.com/kadaliao/open-super-agent/blob/c217b8e0dcaaa40bb865febad2deeba483d0e1cd/docs/events.md#L67-L96)

## 测试与人工验收

- **先自动化。** GitHub 适配器夹具首批返回 PR #41，再返回新建 PR #42 和其可重投事件 E1。断言首批只建基线，E1 重送只产生一笔规则消费及一次可见提醒。让两个轮询者乱序提交，读回游标与事件数。用测试推送源验证签名错误不接纳、持久提交前不确认。
- **区分检查和测试。** 为无变化、检查出错、关键词被过滤、Worker 静默和两个连续命中分别设用例。“现在看一次”在无变化时没有派工。“测试”先查真实变化，未命中时用最近样本或示例实际派工，界面在操作前说明会执行，结果按测试语义标明。[OSA 测试实现](https://github.com/kadaliao/open-super-agent/blob/c217b8e0dcaaa40bb865febad2deeba483d0e1cd/osa/events.py#L506-L519)
- **再由用户桌面验收。** 在有读取授权的测试仓库保存 PR 提醒并建立基线，观察一个后续新 PR。在管理页核对观察及运行，从主会话打开对应发现。暂停 PR 规则后检查另一条周报仍启用。记录规则、事件、运行及消息引用。

## 不在本项范围

自动评论、合并 PR 等写操作需要另行授权。同一 PR 长期工单和“等 CI 通过再继续”见第 14 项。本项交付一个真实来源及通用接入约定，其他平台按需接入。

## 实现与验证

- 聊天与管理表单使用同一规则。GitHub 适配器读取单个已授权仓库最近至多三十个 PR。标题与草稿先做确定性筛选，配置了额外判断条件时对符合条件的新增数据调用模型。详情分别呈现最近检查、筛选、待派工观察、运行和报告。测试源已验证推送先验签再持久接纳，GitHub 当前以轮询接入。
- Go 定向测试覆盖 PR 基线、重复观察、筛选、忙时续接、空查、检查失败、测试样本与同键重试，持久存储测试覆盖较旧游标提交被拒绝。签名夹具覆盖错误签名无观察写入以及正确重投只登记一条观察。公开报告保留已核验的 GitHub 来源链接，测试运行现在会明确标注。
- 真实 GitHub 仓库权限、原生模型语义判断与桌面验收待完成。轮询追溯范围由 GitHub 有界窗口决定。[来源适配器测试](../../../server/internal/eventsource/github_test.go) · [检查与测试回归](../../../server/services/schedule/events_test.go) · [事件记录回归](../../../server/repositories/controllers/automatic_events_test.go)

## 接手说明

先从现有定时和本机 API 触发的登记入口找可复用的运行路径，再接通 GitHub 轮询与两种规则入口。逐项列出自动化事实与用户真实仓库、桌面验收状态。完成本项后停止，后续规格另行启动。
