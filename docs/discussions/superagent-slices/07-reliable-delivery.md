# 07 执行已完成时，重启后仍能收到一次约定报告

## 用户问题

工作结案到报告可见之间可能遇到退出、断线或回执丢失。用户可能一直等不到结果，也可能收到两份。

## 解决方案

在结案时记下该交给谁的结果。重启后核对目标收据，在原地址确认或补交已完成的结果。

## 用户故事

1. 作为用户，我希望 Core 重启后收到已经完成的工作结果。
2. 作为报告收件人，我希望结果送达后即使回执丢失也只看到一次。
3. 作为归档旧会话的用户，我希望从回报仍能知道最初交办的位置。
4. 作为涉及外部动作的负责人，我希望无法查证是否已发送时明确看到待核实，避免重复产生副作用。

## 实现决定

- 业务结论和待投意图在同一提交中登记。投递使用稳定发送键、原始回址及目标确认；本地会话的现有发布收据可复用。
- 普通线程归档或不可达时依原设计核验并回退。先查已收件凭据，再决定是否改址；跨会话只引用来源，不构造无效的本会话回复。
- 已有外部目的地只在具备授权且能核实或支持同键重试时补发。无法确认时保留待核实记录。

## 测试与人工验收

1. 通过业务结案入口，分别在结论落盘后、目标落盘后 ACK 前停止服务再启动。在后一场景先归档原线程，断言用户全局只收到一份报告且工作只执行一次。
2. 覆盖同时领取、不可用目标、外部发送确认未知。分别核实执行次数、交付地址和可观察的收据。
3. 桌面查看自动化故障用例所生成的运行与原会话，核对重启后的结果、条数和来源。

## 不在本项范围

新增外部发送集成、通用消息队列产品、每层函数额外生成请求号。

## 验收记录

- 主会话协议测试以隔离数据库、日志和模拟 Codex 子进程运行。分别在原生终态落盘、宿主输入回执落盘后强制停止 Core，重启后原消息收到一次答复，Worker 只启动一次。
- 普通聊天测试分别在结案落盘后、Chat 写入回件后但数据库尚未记收据时退出。重启后均能在原址核对同一份回件。并发重复恢复仍只确认一次。
- 现有产品通过普通聊天删除入口验证原址不可达。删除前确认原址未收件时，报告送到同一伙伴的主会话并保留原始来源。原址已收件时保留原回执。删除事务失败时两处都回滚。外部结果未知沿用现有 IM 对账和人工重试规则，通过既有定向回归。
- 整单移交后，普通聊天中的回件独立显示实际接手人。原址在接手人产出之前删除时，报告仍送回最初交办伙伴的主会话。原址已经收到报告但回执尚未确认时，删除流程先核对原记录，避免重复回投。
