# 01 首次公开回复前失败时，用户能看到原因并回到原工作

## 用户问题

用户交办后看到伙伴在等待。如果 CLI 尚未公开发言就失败，等待行会消失，只剩自己的交办，看不到失败原因，也没有本轮的伙伴头像可点。

## 解决方案

原交办旁显示本次工作的失败原因和伙伴头像。用户点头像打开当时的工作记录，处理问题后可以在同一来源继续发送。

## 用户故事

1. 作为交办人，我希望等待结束时看到失败原因，以便决定应该重新登录、稍后再试还是补充说明。
2. 作为正在处理多个事项的用户，我希望错误紧跟它所属的交办，以便点开正确的工作。
3. 作为重新打开主会话的用户，我希望之前的失败仍然可见，以便稍后续办。
4. 作为在工作记录里追问的用户，我希望这次追问如果失败，也能从主会话回到这次工作的记录。

## 实现决定

- 仅针对已经接纳并以失败结束，且本轮没有公开伙伴发言的交办。读取同一次执行的终态和公开发言事实，同一来源可以有多轮。接纳前的错误沿用发送表单反馈。
- 错误展示复用原聊天的故障类别、本地化文案与伙伴头像入口。公开页只接收可以公开的稳定错误信息。工作记录保留过程。
- 用户消息保留自己的作者和正文，失败状态附在所属交办旁。只打开记录不触发执行，只有再次发送才开始新回合。

## 测试与人工验收

1. 自动化从主会话发送入口接纳一次交办，让测试 CLI 在公开发言前返回可区分的失败，例如需要登录或额度耗尽。重新读取主会话，断言该行有安全错误、无活动等待，并能按原来源打开历史；在来源续聊，结果仍回到原主会话。
2. 覆盖同一来源两次交办、已经公开发言后失败、主动取消、成功和重读。只有符合条件的交办出现一次失败，同轮公开回件位于另一页也能正确识别。验证原生诊断字符串不会进入公开历史。
3. 桌面由用户验收。在隔离测试账号或可重复的失败配置下，从主会话发送，观察等待结束、原因可读；点伙伴头像打开工作记录，回到主会话或重新打开后仍能找到这次失败。恢复可用配置后在原工作记录继续发送。

## 不在本项范围

忙时排队、自动重试、跨进程补投、全局未读分别在后续完成。

## 接手说明

依托已实现的主会话与来源工作记录。本项状态见[开发与验收索引](README.md)。

### 本项自动化复查

- Go 主会话 API 和领域服务测试覆盖重读、未公开失败、同一来源多轮交办、跨页公开答复与团队负责人变化。SQLite 查询计划用例核对 1 和 100 条交办均按消息、执行和工作标识查询。
- 前端主会话页面、公开消息、来源工作记录、错误本地化四组共 41 个用例通过。覆盖收到工作变化后撤下等待行、显示失败、重新打开页面、点头像导航及在原处发送。公开协议生成检查和前端类型检查通过。
- 隔离 Core 的 HTTP 验收从真实发送入口接纳交办，使用可控 ACP CLI 返回鉴权失败。主会话给出对应错误及实际伙伴，来源保留诊断。随后从原工作记录发送第二条消息，CLI 通过本轮授权公开发言，两次相同调用返回同一收据；重新读取主会话得到两条用户消息和一条伙伴回复。桌面点验由用户完成。
