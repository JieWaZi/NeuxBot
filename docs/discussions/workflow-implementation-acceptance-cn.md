# Workflow 实施与实测记录

本轮在 `工作流分支` 实施，独立 Web 端口 1432、Core 端口 8442。使用隔离验收数据；未合并或推送。以下区分代码验证与真实运行，完整 20 场景通过率尚未测量，不宣称已达到 90%。

## 已落地

- 每轮工作流创作绑定不可变执行上下文；MCP 和 CLI 共用操作目录、授权及幂等回执。新的保存请求形成新版本，原请求重放保留原版本。
- 编译器生成统一 CanvasManifest，包含业务说明、控制关系、数据依赖、现有伙伴和版本化本地脚本。Python 使用真实 stdin/stdout，冻结解释器和脚本版本。
- 画布侧统一原生创作问题及运行问题，动态候选冻结、版本和摘要校验；回答、跳过、过期和取消分别处理。
- 原版本重试、未知效果对账、显式业务成功检查以及有界格式纠正。格式纠正不会重新派发已经完成的业务步骤。
- 默认拖框选阶段，输入框内显示可移除引用，删除同步取消画布选中。阶段内多个步骤使用中性卡片和 Lucide 图标，颜色用于状态及选中，详情呈现业务信息。
- 按用户最终范围删除独立产出页面、卡片、展示声明、专用接口、渲染器及依赖。保留真实运行返回值、Schema 自动输入表单和授权的业务文件交付。

真实验收暴露并修复了 Web 路由拦截内部能力端点、画布抢占下拉 Portal 指针事件、MCP 保存响应遗漏 manifestDigest、引用原始 JSON 进入可见消息等问题。最后两项分别有真实 MCP 桥契约和真实 Core/SQLite 隐藏上下文回归。

2026-10-29 补验：原生 WorkBuddy 续聊不保证重发静态 Instructions，因此引用在不改变可见用户消息的前提下，随每次实际 Runtime 输入注入。换选与上一轮不同的阶段后，仅发送“在本轮选中阶段说明末尾加句号”，模型明确读取本轮稳定目标并只修改该阶段，保存为第 5 版；未再出现 MCP 响应解析错误。完成的选择题显示“方案乙”，不显示内部候选值。
