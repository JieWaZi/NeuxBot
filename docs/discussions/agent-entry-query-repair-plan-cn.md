# 四类入口读取与事件职责收拢实施方案

> 按 [四类入口审计](agent-entry-query-audit-cn.md) 实施。先完成公共执行和热插件，再迁移团队、工作流与知识任务；全部实现后统一审查。用户已自行测试并反馈完成本次实际使用验证。

## 目标与约束

- 正常已有 Chat 热续聊不读取整份 JSONL、不构建全历史消息；幂等、当前执行、原生续接和明确历史交接分别读取真正需要的权威事实。
- 不新增会话身份、门禁、锁、TTL缓存或第二份权威状态。复用原 Chat 操作边界、JSONL 派生文件索引和 Query 事件调度；派生索引可以重建，不反向替代原业务权威。
- 热插件读取只涵盖当前伙伴启用安装、固定版本、程序摘要和配置修订；配置、秘密和实际包只在冷资源取得。插件安装、授权、显式测试及外部插件实现保持原业务职责。
- 同一查询只有一个自动刷新所有者，按真实变化范围更新；消息正文、任务进度、目录、运行状态和日志分别处理。回执负责身份交接和已接纳事实，不能同时触发无条件全局补读。
- 审批、提问、取消、首次进入、缺口/断线恢复、准确版本成果阅读、幂等未知结果恢复保留。冷索引恢复可以重放权威日志，健康热路径不能借用这一恢复流程。
- 不保留旧入口/旧参数/纯转发层作兼容；CLI 特例留原生适配层。已有不相关修改保留，不提交或推送，不操作运行界面。

## 数据与所有权

| 需要的事实                             | 读取职责                                     | 不应顺带取得的数据                             |
| -------------------------------------- | -------------------------------------------- | ---------------------------------------------- |
| 当前 Chat、工作范围、原生会话          | Chat Journal 及原文件索引/查询投影的增量追平 | 全部消息和全部执行收据                         |
| 某 submission / execution 的接纳和终态 | 原身份定位的精确权威范围                     | 其他执行的过程、工具和完整公开消息快照         |
| 新原生会话的历史                       | 明确会话交接时按需、有界读取近期已完成消息   | 热续聊为了比较最后执行而展开全部正文           |
| 当前插件静态声明                       | Repository 对所选伙伴已启用固定版本的窄投影  | 其他伙伴安装、所有历史版本、头像名称、解密配置 |
| 实际账号/插件资源                      | 原冷 Acquire → Bind，所有权交给 Core         | 热回合重复物化或授权探测                       |
| 页面查询事实                           | 原 Query + 统一事件调度                      | 页面/回执/终态各自创建一套刷新责任             |

Core、Host、Environment 不承担数据库扫描与页面失效。Chat/Execution 负责公共权威读取；Channel/Workflow/Knowledge 只补本领域事实，不复制公共执行状态管理。

## 阶段及依赖

### Task 1：公共执行上下文与精确执行读取

负责 `server/services/chat`、`server/services/execution` 中上下文/历史读取及 `server/internal/chat/eventlog` 的原索引查询。保留 JSONL 权威与当前索引恢复语义。

- 先用长历史前缀构造定向失败证据，区分“执行状态读取”与“消息完整投影”。
- 把接纳幂等、当前 Chat/原生续接、单执行结果、近期上下文分离；删除 `LoadExecutionContext` 的宽聚合或将其真正收窄，不保留换名包装。
- 一次接纳使用当前操作边界内取得的状态；不在提交去重、解析、预留后二次解析重复展开全日志。首发回执和续发回执仍准确关联原身份。
- `ReadExecution`、`ReadInitialExecution`、`ReadExecutionOutcome` 使用同一精确执行读取。团队与 Workflow 只消费该公共能力，不再各自做全重放。
- 冷 Resume 的上次插件范围查询定位最后一次执行/继承事实，不再 `ReadRecords` 全读。摘要/重试/文件Diff/真实fork保留其明确输入需求。
- 先向后续任务交付稳定窄读取接口及取消/损坏/快速终态语义，再做定向 Go 检查和并发关键用例。新增/改动结构体全部字段中文注释。

### Task 2：热插件声明与冷物化

负责 `server/services/execution/plugins.go`、插件相关 session_resources 装配和 `server/repositories/controllers/plugin_controller.go` 的执行侧读取；与 Task 1 协调文件段，禁止覆盖其历史查询改动。

- 用真实 SQLite 验证热声明不访问配置/秘密、不展开旧版本和其他伙伴关系，固定版本选择和配置修订仍准确。
- 用执行专用的窄声明替代 `InstalledStates → ReadStates` 管理聚合；实际配置与包只在冷取得时读取，沿现有 Acquire/Bind 交付。
- 保留配置/版本变化对会话兼容的影响、活动资源释放与本轮使用记录；不改插件安装和授权本身，不额外做远端预检。
- 删除执行路径多余的完整 PluginState 复制和装配；管理 API 继续由管理读取实现负责。

### Task 3：目录默认项目查询

由主代理负责 Chat 目录查询和默认项目选择。目录分页不再暗中读取伙伴全部项目引用后去重；用有界候选推进或仅真正进入草稿时独立读取，保留最近有效项目的正确选择。不以固定前N个候选代替完整查找语义。与 Task 1 不重写同一文件段。

### Task 4：团队消息来源与执行观察

公共窄读取交付后，负责 `modules/team`、团队 Chat 页面、`services/channel` 和任务读取。

- timeline Query Key 与线程列表分离；真实生产key测试证明导航不刷新已加载消息页。
- 主 timeline 由一个消息来源拥有，接纳、团队领域事件、Chat终态和恢复统一对账，删除无条件重复导航/详情读取；保留待投递输入和成员报告。
- 负责人和成员 watcher 观察准确执行及持久起点，不从零物化全部公开历史；先订阅后补偿，保证快速完成/重连不丢终态。
- pending follow-up 按 thread、可见性、时间游标在持久层有界读取；避免逐任务读完全部历史再分页。SQL默认单表，确需JOIN必须提供计划与测试。
- 覆盖首发/续聊、已翻旧页、成员任务、审批、取消、缺口恢复；只定向验证。

### Task 5：工作流状态与查询刷新

公共窄执行读取交付后，负责 Workflow API/服务/Repository 与前端 Workflow。

- 真实入口为 WorkflowChatPane → RetainedChatPageContent → ChatPageContent；接纳回执下传已取得事实，不再回执后整日志读取或靠全详情补身份。
- 创作只更新真正变化的定义/会话/版本；终态不无条件刷版本和运行目录。运行日志不刷新整Run和全部实例；同key由统一事件调度拥有。
- worker Inspect 使用公共精确执行查询，完成结果按原首次执行读取，不倒翻全聊天；保留首次接纳身份、授权及保存事务再核验。
- runLoop 复用 Tick 已确认的状态/派发摘要，移除紧接的同聚合重读；版本摘要读取不解码后丢弃完整manifest，已取得revision不再重复读取。
- 删除实际无生产调用的旧刷新/聊天入口，而非增加兜底helper。覆盖创作、阶段批注、Run人工输入/许可、worker审批、取消、重连和日志查询预算。

### Task 6：知识后台任务进度与队列

负责知识服务/前端事件消费，主代理实施或单独子代理处理；与 Task 4/5 并行。

- 任务进度、来源变化、内容发布表达准确变化范围；本地已成功接纳以统一事件刷新，不和HTTP成功回调重复失效整库。无推送远端与未知结果恢复仍有明确对账。
- 仅进度变化不重读未变Wiki目录/主题/正文；首次GET期间变化、隐藏恢复、断线对账仍有效。
- 完整来源选择采用批量范围，避免每10条重复组装全在途占用；核心来源活动查询只围绕实际返回来源。
- 同库只驱动持久队首，完成/取消接续下一项，保留核心跨进程文件锁，不让每个等待任务50ms争抢。
- 真正需要整库输入的算法读取保留；非Wiki任务不加载无用Wiki页。若需改独立知识核心，应在其仓库实现并固定可发布版本，禁止手改module cache或只依赖go.work掩盖。
- GenerateText 每调用、ExecuteTask 每任务的Temporary合同不变；不把它们串成泄漏上下文的普通Chat来节省启动。

### Task 7：统一审查、契约与文档

- 所有实现完成后一次并行审查，范围以本轮修改前实存快照为基线，不把主仓库历史dirty当作本轮差异。
- 针对已确认发现集中修复，再只审修复差异；不反复跑无关全量检查。
- 协议由唯一生成命令更新，运行 api:check、受影响Go包/前端定向用例、类型/lint、Core构建及docs:check。
- 更新架构、事件职责与本审计每项结果，记录确定查询/读取预算与真实验收边界。用户已反馈完成本次实际使用测试，自动化与用户反馈分别记录。

## 并行文件边界

| 任务组合  | 共享处                      | 处理方式                                                           |
| --------- | --------------------------- | ------------------------------------------------------------------ |
| 1 / 2     | session_resources.go        | 1仅精确历史定位段；2仅插件冷取得段，先沟通后编辑                   |
| 1 / 3     | chat.go / event_pipeline.go | 1只权威上下文；3只目录与默认项目，避免整文件替换                   |
| 1 → 4 / 5 | 精确执行事实接口            | 先交付稳定接口，后续不再复制状态读取                               |
| 4 / 5 / 6 | 公共Query事件工具、生成契约 | 公共工具改动由主代理协调；生成一次统一执行，领域代码不并发改生成件 |
| 全部      | 文档 / 最终验证             | 主代理统一更新，不让子代理反复全仓review或覆盖其他线程             |

本方案不要求新增第三种技术会话、身份或缓存层。实现中的具体函数名由责任模块自行确定，但不得以保留宽读取、增加转发层或更长缓存替代上述职责拆分。
