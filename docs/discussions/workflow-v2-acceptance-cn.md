# Workflow V2 能力对齐与验收

本文配套 [V2 架构与设计](workflow-v2-design-cn.md)，将“达到 QoderWake 90% 以上效果”落实为可以对照的任务与交互验收。目标覆盖用户关心的创作、画布、动态问答、脚本、伙伴、结果和恢复；不以 UI 皮肤相似度、代码量或节点名称计分。

当前只有设计和参考研究，没有 V2 产品实现，**V2 通过率尚未测量**。本表不是参考产品全部功能清单；交付前须复核其与用户目标相关的能力，发现遗漏时补入基线，不能通过删减失败场景提高分数。

## 1. 参考证据与能力边界

| 能力                              | 参考证据                                               | V1 现状                                  | V2 目标                                       |
| --------------------------------- | ------------------------------------------------------ | ---------------------------------------- | --------------------------------------------- |
| 工作流内持续创作                  | 页面编辑对话、空参数 get_script 成功                   | 正确入口已有 session 绑定；跨入口待定位  | 所有创作入口、续聊和恢复一致绑定              |
| 完整源码及增量修正                | script 与 baseDigest+patches 的实际保存                | 已有完整源码保存，缺 Patch 管线          | 两种输入共用校验、CAS、回执                   |
| 保存后新版本和画布                | 实验版本 1—4 与原流程多个修正版本                      | 版本和 Manifest 已有，重复内容 unchanged | 显式新保存生成新版本，画布同步                |
| 保存拒绝和修复                    | 系统 Waker 不可用于流程被拒绝，换已有伙伴后保存        | 部分编译/策略检查已有                    | 准确定位、有限自动修复、无半生效              |

| 取消和主动跳过                    | 取消实测；skip 在事件里被混为 timeout                  | 有原始状态/接口基础                      | 明确保留来源和终态，不复制观察到的不一致      |
| Schema 自动修正、全部节点恢复策略 | 仍未知                                                 | 部分 retry 和错误协议                    | 发布自己的有界契约并实测，不凭猜测宣称对齐    |

“V1 有基础”不计作 V2 已通过。“参考未知”也不自动计为我方领先或不需要验收；先保留自有质量要求，再继续核实相关行为。

## 2. 计分与硬门槛

首版采用 20 个完整场景，每项 5 分，总分 100。每项的正向、反向和证据要求均通过才得分；部分完成、未知、mock 通过或只有代码实现均为 0 分。

达标需要同时满足：

- 总分至少 90，且全部标为“必须”的场景通过。
- 没有错对象写入、未授权执行、未知效果盲重放、虚假保存/交付成功等阻断问题。
- 真实任务覆盖至少一条原生工具适配与一条 CLI 路径；确实不支持某能力的 Runtime 应在产品入口准确表达，不宣称该组合已通过。
- 评分基线在实施前冻结；新增与目标相关的参考能力需显式更新表及权重，不在验收后调整分母。
- 如同一错误可在多轮修正、刷新或重启后稳定复现，相应场景不得以一次偶然成功计分。

## 4. 真实场景包

按同一批固定样本在参考产品和 V2 上分别记录过程，不使用真实生产密钥或不可撤销的业务操作。

1. **数据同步型**：缺参数→查询目录→用户多选→脚本分页同步虚构数据→已有伙伴校验及摘要→真实文件交付。包含无变化、部分失败和缓存配置分支。
2. **多伙伴分析型**：独立伙伴并行分析→逐项验证→汇总；验证字段不合规、部分任务失败和子流程展开。
3. **故障修正型**：明确的 argv/路径错误→运行失败→原版本重试→基于证据修正→新版本通过，保留每一轮历史。
4. **恢复型**：问答和脚本运行期间断开页面、停止运行、重启 Core；检查请求身份、输出和未知效果。

每轮保存任务描述、源码/版本摘要、实际工具参数与脱敏响应、事件游标、用户操作、最终产出和耗时。模型最终总结不能替代这些事实。

## 5. 交付报告

交付报告逐项给出 pass/fail/not_run、证据链接、Runtime/账号/模型组合和剩余差异，分别报告功能分数、硬门槛和真实视觉验收。若只完成自动化检查，就明确尚未取得真实场景分数。

用户不需要以肉眼猜测是否达到 90%；必须能从同一组任务、工具和画布行为判断效果是否接近参考产品。出现阻断项时继续修复，不用总分掩盖关键链路失败。
