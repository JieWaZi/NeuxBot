# 聊天存储的容量与分页设计依据

本次重构保留 JSONL 作为消息权威，重新设计提交批次、原生正文引用和可重建的磁盘定位索引。目标是避免重复正文与全历史扫描，同时保留恢复、永久幂等和准确用量所需的事实。完整约束见 [重建方案第 6.3 节](../../superpowers/specs/2026-11-04-agentruntime-rebuild-design.md#63-磁盘占用分页与恢复成本)。

## 现有实现的实测基准

以下为合成 ASCII 内容，在 macOS arm64、APFS 的同一临时目录中运行旧 eventlog 的实际写入与分页 API；不含真实会话或模型调用。正文长度只统计最终用户输入、助手答复和工具正文，不能把日志与正文的差额全部解释成重复内容：日志还承担身份、业务事实、提交和恢复职责。

| 样本                              |    最终正文 |        JSONL |      原索引 | 观察                           |
| --------------------------------- | ----------: | -----------: | ----------: | ------------------------------ |
| 12 轮短聊天                       |     3,648 B |     13,399 B |     6,488 B | 小消息主要受元数据影响         |
| 1 MiB 答案，128 个片段            | 1,048,624 B |  1,069,469 B |    11,856 B | 日志加索引约为正文的 1.03 倍   |
| 512 KiB 工具正文，20 次进度及终态 |   524,336 B |  1,054,269 B |     2,440 B | 差量有效，终态仍重复一份大正文 |
| 10,000 轮，60,001 条记录          | 3,040,000 B | 11,100,079 B | 5,280,152 B | 索引约占两个文件总长的 32%     |

旧作用域编码在短聊天中减少了约 24% 的日志字节；工具前后缀差量在上述工具样本中减少了约 90% 的日志字节。这些机制有实际收益，应保留其语义，而不是为重写而改成逐事件完整快照。

长历史每次读取 20 条消息，实际读取约 11 KB 正文，同时读取约 5.33 MB 索引。原因是晚到文件成果查询会扫描完整索引。缺索引恢复又会先读完整日志，再逐行重读建索引。这两个成本应分别改成按消息定位，以及一次有界扫描重建。

文件长度之外还要计算分配空间。同样 1,000 条、每条 308 B 的记录，逐调用单独建文件实占约 4.10 MB；16 个固定分片约 0.33 MB。该实验不含目录和索引，说明小文件有明确块放大，不能据此把分片数固定为 16；正式布局需连同并发、重建范围和定位库一起测量。

## 存储设计取舍

JSONL 采用追加语义，避免不断保留增长中的完整正文快照。存储成本须结合最终正文、元数据、索引和恢复职责分别测量。

分页先按排序索引选择消息，再读取选中正文；近期消息有内存预算。这个定位方式值得吸收。其部分查询仍统计全部较早消息的数量，本项目无需为每页游标读取附带同样的全前缀计数。

用量记录保留调用事实的独立生命周期，以原生调用身份唯一归账，不能因聊天投影重放、多个输入被同一次执行消费或删除聊天而重复计量或丢失历史用量。

源码推导的序列化量不代表设备实际写入量。

## 重建后的存储边界

- 原生片段、最终正文与主用量由同一个 Store 保存规范事实；公开 Chat 保存关系与引用。相同终态不再重复写入全文，真正校准必须表达明确替换。
- 流式显示与耐久提交分开。按消息、语义边界和有界字节预算合并新增片段，不能将每个 Token 写成独立耐久批次，也不能不断追加增长中的全文。
- 工具差量限制依赖深度，并提供完整恢复起点。历史页定位当前有效版本，不能为显示一个最终状态展开全部旧快照。
- JSONL 完成同步后才发布批次版本和派生定位。半个批次不能对读者可见；同键重试返回原回执，同键异内容拒绝。
- 单一 SQLite 定位库存流覆盖、记录位置、批次回执位置和消息锚点，不存第二份正文或主用量。长身份共享存储，记录使用紧凑引用。库丢失可以从 JSONL 重建。
- 分页使用游标和有界批量定位；索引不能整份常驻内存后以缓存命中率掩盖冷读全扫，也不能每条消息各发一串重复查询。

这仍有成本：索引增加了精确消息、执行和输入反查能力；原子批次增加了幂等与完整性元数据。不能要求不同耐久语义的格式只按文件长度比较，也不能只因读取变快就忽略索引体积上涨。

## 验收口径

用同一业务事实分别测试短聊、长文本、大工具、长历史和大量短原生调用。报告日志长度、索引长度、文件数量、实际分配空间，以及写事务临时日志峰值；区分普通合批与每小片段单独提交的压力场景。

分页同时报告固定页大小下的耗时、分配内存、读取正文量、SQLite 查询数和实际查询计划。SQLite 返回行数不等于底层物理读取字节；没有 VFS 或设备观测时不能声称测得了总磁盘 I/O。保留索引的重开、缺索引重建与不完整尾部恢复单独测试。

性能通过还必须满足重试幂等、CAS、崩溃恢复、旧日志读取、有序消息投影、终态校准和原生用量不重复。聊天删除不能顺带删掉仍需保留的原生调用事实。原生正文的保留期限、历史压实与空间回收需要独立的引用和保留规则；本轮不以删除幂等回执或默认压缩活跃日志换取表面容量下降。
