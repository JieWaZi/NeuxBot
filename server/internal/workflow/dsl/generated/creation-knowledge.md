# NeuxBot Workflow SDK ally.workflow/2

The source is authoritative. Use stable ASCII IDs for phases, nodes, groups and actions. Never change an existing ID just to rename its label. Meta is a pure JSON literal. Worker identities, schemas and tool policies must be statically resolvable.

The host compiles main logic to durable Go instructions, with JSON value semantics. This is a restricted DSL, not a full JavaScript VM. Assignment and captures copy values; do not write outer mutable captures from parallel tasks. Strings use Unicode code points. Regular expressions use the RE2 common subset (g/i/m/u). Date is frozen to run start. Math.random is unavailable in orchestration. Put general JavaScript or Python into functionTask.

Function code is a complete program, not a bare function body: JavaScript must declare function main(input) { return JSON; }; Python must define def main(input): and return a JSON value. JavaScript main must be synchronous. Do not put a top-level return in the code string. Only the returned value is the Function result. Node outputSchema is optional. If supplied, use a JSON literal or a top-level literal constant; property access such as meta.outputSchema is not statically resolvable. Omit it only when node-level output validation is unnecessary.

Every user-facing inputSchema property must include a short title and a concise description in the user language. The input-parameter preview shows the title and description separately. Titles are noun phrases, ideally 2-10 Chinese characters or 1-4 words; descriptions are one short sentence, ideally at most 40 Chinese characters or 20 words. State what to provide and only the essential format, unit or missing-input behavior. Do not repeat the title, prefix text with required/optional, add long parenthetical explanations or describe the whole workflow. Express requiredness only through the schema required array and actual default values through schema default. Keep detailed business rules, branches and follow-up questions in worker instructions or workflow logic; preserve essential user-facing constraints in concise wording. For example, title: Requirements, description: Paste the current requirements.; title: Environment, description: Provide one environment and version per line.; title: Approval threshold, description: Ask for approval when remaining high-risk items reach this count., default: 1. Include only inputs needed for the user goal, and reuse these concise labels and descriptions when summarizing parameters in chat. Use stable keys for code, never as the only form label. Declare file inputs and final file outputs as {type: 'string', format: 'file', title, description}. Arrays use items with this same file schema. Input forms upload files and run admission replaces uploaded ally-file references with real absolute paths in the approved run scope. Workers must read those paths using actual tools; never treat references as file contents. Final file values must be paths to real files created inside flowContext.scope.workingDirectory; the user and automatic task API can download these files. Return actual paths rather than base64 data or made-up download URLs. Ordinary strings are never inferred to be file outputs. Input form controls support x-ui-control: input or textarea for strings, radio or select for scalar enum, switch or checkbox for booleans, and checkboxes for arrays whose items.enum lists the allowed values. x-ui-labels supplies user-facing choice labels in enum order. These annotations only select controls; values still follow the declared JSON Schema types and constraints. Use these same annotations in askUser schemas.

Await workers, human inputs, actions and child results. Parallel returns in input order. Pipeline advances each item immediately after its own preceding stage, then joins all items in original order. A null stage result is ordinary JSON, not a failure. Explicit throw stops the failed item.

Human defaults do not submit or approve. Approvals require a positive explicit value; skip and timeout preserve their source. Actions use separate operation permissions.

Worker chats use the same managed runtime workspace and native instruction-file loading as ordinary chats. Their runtime working directories are isolated; the approved business directory is shared through project links and additional directory authorization. Build shared file paths from flowContext.scope.workingDirectory and pass those absolute paths to worker prompts and results. Never assume two workers have the same process working directory. Use run-specific output paths, require actual tools to create and read deliverable files, and verify existence and nonempty content.

A structured worker must call allycli workflow results submit with a stable --request-id and an input JSON object whose data matches its schema. A submission is only a candidate until its Execution succeeds. Do not rely on JSON pasted into a final reply. For a root file schema, data is the actual file path. Add routing or summary fields only for real downstream consumers.

When the user requests delivery to WeChat or Feishu, discover approved chats with allycli workflow resources list --kind imTargets. Discover the native IM operation through allycli workflow resources list --kind builtinActions, tool im_delivery, through a builtin action declaring its connector ID and awaiting ctx.callTool({callId, connectorId, toolName: 'im_delivery', input: {action: 'deliveries.create', targetId, content, files}}). Fixed literal targetIds are derived as workflow resource dependencies. Dynamic targetIds must declare the approved imTargetIds on the builtin action; runtime delivery cannot use an undeclared target. Admission checks these targets before any node runs. This durable action waits for delivery acceptance; query deliveries.get to verify sent, failed or unknown status. Never invent recipients or connector IDs. Resource IDs come from allycli workflow resources list; never invent or silently replace them. Do not send messages or publish outside an explicitly authorized action.

When optimizing a failed run, read all allycli workflow evidence list pages, including run.failure, instance failures and actionCalls. Inspect nested cause, hint, sourceRange and delivery receipts including partsSent and unknown status before proposing a repair. Preserve original call identities and never repeat an already completed or uncertain external operation. Read the current revision and pending annotations before saving. Validate complete source, fix diagnostics, then allycli workflow source save using expectedRevisionId and a stable requestId. At most three repair attempts per turn. Only the tool save receipt proves the source is active.


Declare user-provided values in meta.inputSchema and consume them through args. Give every input a concise title and description in the user language. Keep secrets and placeholders out of defaults. Declare file references with type:string, format:file; a reference is not file content.

Python requires a configured interpreter and executionMode:trusted_local. JavaScript supports pure execution. Authoring prepare includes functionLanguages when language is python.

JavaScript/Python functionTask defaults to 600000 ms (10 minutes), with the same hard maximum. Omit timeoutMs unless the user agreed to a shorter deadline. The entire run has a separate 24-hour host deadline; do not invent a shorter overall budget.

Workers have no independent timeout; worker timeoutMs is unsupported. User cancellation and actual execution failure remain effective.

HTTP actions default to 30000 ms. Command/script actions default to 600000 ms, with the same hard maximum. Omit timeoutMs unless the user agreed to a shorter deadline.

source save compiles and validates complete source, checks policies and expectedRevisionId, then commits an immutable revision and its receipt together. Use --source for the UTF-8 file and a stable --request-id. A successful immediate receipt with saved:true, revisionId and sourceDigest proves saving. Explicit saves create a new immutable revision, including unchanged source; replaying the same request returns the original receipt. If the response is lost, query receipts get for the original operation/request ID. Read current source again on revision conflict. Saving does not prove a real run or external delivery succeeded.

Run budgets have different meanings: limits.concurrency caps simultaneous external calls, while limits.maxInstances caps the cumulative number of node instances in the entire run, including actions, functionTask, workers, human requests and child-workflow calls. Every loop iteration or batch task consumes additional instances; phase and log do not. Serial execution uses concurrency:1, never maxInstances:1 for a multi-step workflow. Unless the user requested a smaller total budget, omit maxInstances to use the bounded host default. If declaring it, count all required steps and allow for loops, batches and branches. The compiler rejects budgets below a provable minimum path, but dynamic paths may require more.

Name every node label for its business purpose in the user's language. Add an optional static description (at most 500 Unicode characters) as one sentence explaining what the step does for the user. Cards and details share this description. Do not label or describe a business step using implementation terms such as Function, python or trusted_local; those belong only in technical details. Missing action descriptions may reuse meta.actions description; other nodes have no invented description.

Workers return final text without schema, or matching JSON directly with schema. There is no data/content/analysis wrapper; values can be read by later nodes and the final return.

V2 exports static meta and optional scripts. Each script has language:python, protocol:json or text, and complete code as a string or interpolation-free String.raw template. Code bytes are frozen in the revision. A script action references scriptId. The host writes the complete input JSON value to stdin (missing input is null, false/0/empty string remain values). JSON stdout must contain exactly one value; stderr is logs. Text stdout is returned as a string. No automatic pip install. Script actions return {data,durationMs,process}.

Use explicit kind:text/select/multiselect/form/confirm. choices may be a dynamic {value,label} array from a prior node or a candidate fileRef; the host freezes the evaluated snapshot. kind:form requires schema and excludes choices. allowCustom defaults false; allowSkip defaults false. Multiselect defaults minSelections:1 and maxSelections to candidate count; explicit minSelections:0 allows empty selection. HumanAnswer contains questionId,status,source,value?. Defaults only prefill. onTimeout defaults fail; explicit skip returns timed_out without value, default returns timed_out with validated defaultValue. Confirm can never auto-approve via timeout/default. Cancellation throws. Cache replay preserves original status/value and references the original answer.

successCondition:{path,equals} checks the validated business value: action.data, direct worker JSON/text, or functionTask result. path is a JSON Pointer; equals is a literal JSON value. Failed checks throw BUSINESS_CHECK_FAILED. Ordinary false and null are data without an explicit check.

Host budgets from the shared contract: source 1048576 bytes; node business output 1048576 bytes; inline human choices 500 items and 262144 bytes; script action deadline at most 600000 ms. Truncated stdout is never accepted as successful JSON. Use managed file references for larger results.

Group failureMode defaults fail-fast. collect-null returns null for failed items in input order, retaining failure identity and diagnostics on original instances; ordinary JSON null is not failure.
